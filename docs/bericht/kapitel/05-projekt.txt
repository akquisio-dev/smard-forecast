# Das Vorlaufzeit-Problem

Dieses Kapitel ist der Kern des ganzen Projekts.

!merke
Ein Modell muss mit genau den Vorhersagen trainiert werden, die es im Betrieb bekommt. Eine Prognose für Tag 5 lernt man nur aus früheren Vorhersagen, die ebenfalls 5 Tage Vorlauf hatten.
!ende

## Warum das so wichtig ist

Kapitel 8 hat gezeigt: Eine Wettervorhersage mit 5 Tagen Vorlauf liegt deutlich öfter daneben als eine mit einem Tag. Trainiert man ein Modell mit fast perfekten Wetterdaten (etwa mit Messungen oder Vorhersagen mit nur wenigen Stunden Vorlauf), lernt es: „Wenn 800 W/m² angekündigt sind, kommen auch 800.“ Im Betrieb bekommt es dann eine 5 Tage alte Vorhersage von 800 W/m², vertraut ihr genauso, und gibt eine viel zu schmale Bandbreite aus. In der Prüfung sähe alles gut aus, weil die Prüfdaten ebenso fast perfekt wären. Im Betrieb wäre es schlecht und wüsste es nicht.

## Die Archive von Open-Meteo

!begriff Open-Meteo: ein freier Dienst, der die Ergebnisse vieler Wettermodelle (darunter alle ICON-Modelle des DWD) über eine einfache Schnittstelle im Internet bereitstellt, für aktuelle Vorhersagen und für die Vergangenheit. Die Daten stehen unter CC BY 4.0.

Open-Meteo bietet drei Archive, die für dieses Projekt in Frage kommen:

Tabelle: Archive von Open-Meteo
| Schnittstelle | was sie liefert | geeignet? |
| Historical Forecast API | für jede vergangene Stunde den Wert aus dem jüngsten Lauf; also fast immer mit 0 bis 6 Stunden Vorlauf | nein: viel zu optimistisch, genau die Falle von oben |
| Previous Runs API | für jede Stunde zusätzlich den Wert aus dem Lauf von 1, 2, ... 7 Tagen vorher, als eigene Spalten `..._previous_day1` bis `..._previous_day7` | ja |
| Single Runs API | einen ganzen Lauf mit exaktem Startzeitpunkt | nur ab Mai 2026; für Prüfungen |

[abb vorlauf_schema | Oben: die Historical Forecast API nimmt für jede Stunde den jüngsten Lauf. Unten: die Previous Runs API nimmt für Tag 3 den Lauf, der mindestens 72 Stunden vorher begann (Schema).]

## Was „Tag N“ genau bedeutet

Die Dokumentation von Open-Meteo sagt nicht genau, welcher Lauf hinter `previous_day3` steckt. Deshalb wurde es am 2. November gemessen: Für einen Ort (52,5° N, 10° O) und alle Stunden des 20. Oktober 2026 wurden die Werte der Previous Runs API mit allen Einzelläufen der Woche davor verglichen, Wert für Wert, mit Temperatur und Wind.

Tabelle: Ergebnis des Abgleichs
| Spalte | passt genau zu | Vorlauf |
| previous_day3 | dem Lauf 3 Tage vorher | 72 bis 77 h |
| previous_day6 | dem ICON-global-Lauf 6 Tage vorher | 144 bis 150 h |
| previous_day1 | keinem Einzellauf genau; Abweichung wenige Zehntel Grad | etwa 24 bis 27 h |

Daraus folgt, was „Tag N“ im Training bedeutet: **der neueste Lauf, der mindestens N mal 24 Stunden vor der Zielstunde gestartet ist.** Die Vorlaufzeit liegt also zwischen N · 24 Stunden und N · 24 Stunden plus dem Abstand zwischen zwei Läufen (3 bis 6 Stunden), im Mittel etwa bei N · 24 + 3 Stunden.

## Vom Training in den Betrieb: interpolieren statt abrunden

Im Betrieb nimmt das Tool für jede Zielstunde die neueste verfügbare Vorhersage. Deren Vorlauf L kann jede Stundenzahl haben, zum Beispiel 95 Stunden. Die erste Fassung dieses Plans wollte L einfach auf ganze Tage abrunden: 95/24 = 3,96, abgerundet Tag 3. Das wäre falsch gewesen, und der Betreuer hat den Fehler bei der Durchsicht gefunden: Tag 3 wurde nur mit Vorhersagen von 72 bis 77 Stunden gelernt. Eine 95 Stunden alte Vorhersage ist fast so unsicher wie Tag 4. Das Modell hätte ihr zu sehr vertraut, und die Bandbreite wäre zu schmal geworden. Genau das Problem, das dieses Kapitel vermeiden will, wäre durch die Hintertür zurückgekommen.

Die Lösung ist, zwischen den beiden benachbarten Vorlauftagen zu **interpolieren**:

$$ x = \frac{L - 3\,\mathrm{h}}{24\,\mathrm{h}}, \qquad N = \lfloor x \rfloor, \qquad w = x - N

$$ \hat{y} = (1 - w)\cdot f(\mathrm{Tag}\ N) + w \cdot f(\mathrm{Tag}\ N{+}1)

!begriff Interpolation: einen Wert zwischen zwei bekannten Werten schätzen. Linear interpolieren heißt: auf der geraden Linie zwischen beiden. Liegt x zu 83 % des Wegs von 3 nach 4, nimmt man 17 % des Werts bei 3 und 83 % des Werts bei 4.

!begriff Abrunden ⌊x⌋: die größte ganze Zahl, die nicht größer als x ist. ⌊3,83⌋ = 3.

Darin ist f(Tag N) die Vorhersage des Modells, wenn man ihm „Vorlauftag N“ als Merkmal gibt, und die 3 Stunden ziehen den mittleren Versatz der Trainingsdaten ab. Liegt x unter 1, wird Tag 1 genommen; über 6 gibt es keine Vorhersage. Nach dem Interpolieren werden p10, p50 und p90 wieder der Größe nach sortiert.

!rechnen Zwei Zielstunden im Betrieb
Der neueste ICON-Lauf begann am 2. November um 12:00 UTC.
Zielstunde 5. November, 15:00 UTC: L = 75 h. x = (75 − 3)/24 = 3,0, also N = 3 und w = 0. Das Modell bekommt reinen Tag 3, genau wie im Training.
Zielstunde 6. November, 11:00 UTC: L = 95 h. x = (95 − 3)/24 = 3,83, also N = 3 und w = 0,83. Vorhersage = 0,17 · f(Tag 3) + 0,83 · f(Tag 4). Abgerundet hätte man reinen Tag 3 genommen.
Zielstunde 2. November, 20:00 UTC: L = 8 h, x < 1, also Tag 1. Das ist vorsichtig: Eine 8 Stunden alte Vorhersage ist besser als eine mit 24 Stunden Vorlauf, das Modell nimmt also eher eine zu breite Bandbreite an.
!ende

!praxis Wie das geprüft wird
Ob die Interpolation die Trefferquote wirklich hält, wird in Abschnitt 23.4 gemessen: Die Single Runs API liefert seit Mai 2026 ganze Läufe mit exaktem Startzeitpunkt. Damit kann man für jeden Vorlauf in Stunden (nicht nur in ganzen Tagen) die Trefferquote ausrechnen, einmal mit Interpolation, einmal mit Abrunden. Diese Prüfung gehört zu Phase 4.
!ende

Dass Tag 1 nicht exakt passt, liegt sehr wahrscheinlich an ICON-D2-RUC (Kapitel 8). Open-Meteo nutzt für die ersten Stunden inzwischen diese stündlich aktualisierte Variante, und die Single Runs API meldete bei ihren Fehlermeldungen genau dieses Modell. Für das Training ist das unkritisch. Das eigene Archiv (Kapitel 20) speichert die Startzeitpunkte aller ICON-Modelle mit, damit sich die Frage später klären lässt.

## Warum es Tag 7 nicht gibt

Die Spalten `previous_day7` sind in allen Stichproben leer, 2024 genauso wie 2026. Der Grund: Ein Lauf, der mindestens 7 · 24 = 168 Stunden vor der Zielstunde begann, müsste bis mindestens 168 Stunden vorausrechnen. ICON global rechnet nur 180 Stunden voraus, und das nur bei den Läufen um 00 und 12 UTC. Für viele Zielstunden reicht kein Lauf so weit, und Open-Meteo führt die Spalte deshalb gar nicht. Im Betrieb dagegen gibt es Tag 7 teilweise: Die aktuelle Vorhersage reicht etwa 7,5 Tage. Weil es dafür aber keine Trainingsdaten gibt, kann das Modell ihn nicht lernen. Version 1 geht deshalb bis Tag 6; Tag 7 kommt, wenn das eigene Archiv ein Jahr umfasst (frühestens November 2027).

# Datenquellen und Schnittstellen

## Was eine Schnittstelle ist

!begriff API: application programming interface, eine Schnittstelle, über die ein Programm ein anderes nutzt. Hier immer eine Web-API: Man ruft eine Internetadresse (URL) auf und bekommt Daten zurück, meist im Format JSON.

!begriff HTTP: das Protokoll, mit dem Browser und Programme Daten im Internet abrufen. Eine Anfrage (Request) nennt eine URL; die Antwort (Response) hat einen Statuscode (200 = alles gut, 429 = zu viele Anfragen, 500 = Fehler beim Server) und einen Inhalt.

!begriff JSON: JavaScript Object Notation, ein Textformat für strukturierte Daten aus Objekten in geschweiften Klammern (Schlüssel und Wert), Listen in eckigen Klammern, Zahlen und Texten. Menschen können es lesen, Programme leicht verarbeiten.

### Eine Anfrage an Open-Meteo, zerlegt

```
https://previous-runs-api.open-meteo.com/v1/forecast      Server und Pfad
  ?latitude=48.14&longitude=11.58                          Ort (München)
  &models=icon_seamless                                    Wettermodell
  &start_date=2025-01-01&end_date=2025-12-31               Zeitraum
  &hourly=shortwave_radiation_previous_day1,               Spalten: Variable
          shortwave_radiation_previous_day2, ...                    je Vorlauftag
  &timezone=GMT                                            Zeitstempel in UTC
```

Die Antwort ist ein JSON-Objekt mit einer Liste von Zeitstempeln und für jede Spalte einer gleich langen Liste von Werten; fehlende Werte stehen als `null`.

```
{"latitude": 48.14, "longitude": 11.58, "elevation": 519.0,
 "hourly": {"time": ["2025-01-01T00:00", "2025-01-01T01:00", ...],
            "shortwave_radiation_previous_day1": [0.0, 0.0, ..., 212.0, ...],
            "shortwave_radiation_previous_day2": [0.0, 0.0, ..., 198.0, ...]}}
```

### Abrufgrenzen und Gewichtung

Ein freier Dienst muss sich vor Überlastung schützen. Open-Meteo erlaubt ohne Bezahlung 600 Abrufe pro Minute, 5.000 pro Stunde und 10.000 pro Tag, für nicht-kommerzielle Nutzung. Große Abrufe zählen dabei mehrfach: anteilig mehr ab 10 Spalten und ab 14 Tagen Zeitraum, und jeder Ort zählt einzeln. Im Projekt steht dafür die Funktion `gewicht()` in `sf/openmeteo.py`:

$$ w = n_{\mathrm{Orte}} \cdot \max\left(1,\ \frac{n_{\mathrm{Spalten}}}{10}\right) \cdot \max\left(1,\ \frac{n_{\mathrm{Tage}}}{14}\right)

!rechnen Was ein Jahr München kostet
6 Variablen · 6 Vorlauftage = 36 Spalten, ein ganzes Jahr = 365 Tage, ein Ort.
w = 1 · (36/10) · (365/14) = 3,6 · 26,07 = 93,9. Ein einziger Abruf zählt also wie 94 kleine.
Ein Ort mit Solar und Wind (10 Variablen, 60 Spalten): w = 6 · 26,07 = 156.
!ende

## SMARD

Die Daten von SMARD kommen über eine Schnittstelle, die auch die Diagramme auf smard.de speist. Sie arbeitet in zwei Schritten:

1. **Inhaltsverzeichnis holen.** `https://www.smard.de/app/chart_data/4068/DE/index_hour.json` liefert für die Reihe 4068 (Solar), Region DE und stündliche Auflösung eine Liste von Zeitstempeln. Jeder steht für ein Stück von einer Woche.
2. **Wochenstücke holen.** `.../4068/DE/4068_DE_hour_<Zeitstempel>.json` liefert `{"series": [[Zeitstempel, Wert], ...]}` mit Unix-Zeit in Millisekunden (Kapitel 4) und dem Wert in MWh, oder `null`, wenn noch nichts veröffentlicht ist.

## Energy-Charts

Energy-Charts (Fraunhofer ISE) liefert die installierte Leistung monatlich, abgeleitet aus dem Marktstammdatenregister, über `api.energy-charts.info/installed_power?country=de&time_step=monthly`. Für Solar gibt es DC (Module) und AC (Wechselrichter); das Projekt nimmt AC (Kapitel 6).

## Git, GitHub und der Deploy-Key

!begriff Git: ein Programm zur Versionsverwaltung. Jeder gespeicherte Stand heißt Commit und hat eine eindeutige Kennung (zum Beispiel `163d455`), eine Beschreibung und einen Verweis auf den vorherigen Stand. So lässt sich jede Änderung nachvollziehen und rückgängig machen.

## Parquet: wie die Daten gespeichert werden

!begriff Parquet: ein Dateiformat für Tabellen, das Spalte für Spalte statt Zeile für Zeile speichert [@parquet]. Gleichartige Werte liegen nebeneinander und lassen sich stark komprimieren; außerdem kann man einzelne Spalten lesen, ohne die ganze Datei zu laden.

[abb l_parquet | Zeilenweise gegen spaltenweise Speicherung (Schema).]

Die Wetterdaten liegen in der „langen Form“: eine Zeile je Stunde und Vorlauftag, Spalten `zeit` (UTC), `vorlauf` (1 bis 6) und je Variable eine Spalte. Zahlen werden als 32-Bit-Gleitkommazahlen gespeichert; sie haben etwa 7 gültige Stellen, mehr als jede Wettervorhersage genau ist, und brauchen halb so viel Platz wie die üblichen 64 Bit.

!begriff Gleitkommazahl: die Art, wie Computer Kommazahlen speichern: als Ziffernfolge (Mantisse) und Zehner- beziehungsweise Zweierpotenz (Exponent). 32 Bit reichen für etwa 7, 64 Bit für etwa 16 gültige Dezimalstellen.

## systemd: Dienste und Zeitgeber

!begriff systemd: das Programm, das auf Linux-Servern alle Dienste startet, überwacht und protokolliert. Ein Dienst wird in einer kleinen Textdatei beschrieben, der Unit-Datei.

!begriff Timer: eine systemd-Unit, die einen Dienst zu festgelegten Zeiten startet, ähnlich einem Wecker. Anders als der ältere cron holt ein Timer verpasste Termine nach (`Persistent=true`), etwa nach einem Neustart.

Der Archiv-Job besteht aus zwei Unit-Dateien. Hier die wichtigsten Zeilen mit Erklärung:

```
[Service]
Type=oneshot                   läuft einmal durch und endet
User=smard-forecast            eigener Benutzer ohne Anmeldung, keine Root-Rechte
ExecStart=/usr/bin/python3 -I /opt/smard-forecast-archiv/archiv.py
StateDirectory=smard-forecast  systemd legt /var/lib/smard-forecast an, nur dort darf geschrieben werden
ProtectSystem=strict           der Rest des Dateisystems ist schreibgeschützt
ProtectHome=yes                keine Sicht auf Home-Verzeichnisse
NoNewPrivileges=yes            kann sich keine Rechte verschaffen
CapabilityBoundingSet=         keinerlei Sonderrechte
RestrictAddressFamilies=AF_INET AF_INET6   nur normales Internet, keine anderen Kanäle
MemoryMax=256M                 höchstens 256 MB Speicher

[Timer]
OnCalendar=*-*-* *:35:00       jede Stunde um :35
RandomizedDelaySec=120         plus bis zu 2 Minuten Zufall, damit nicht alle gleichzeitig fragen
Persistent=true                verpasste Termine nachholen
```

!warum Warum so viele Einschränkungen?
Das Prinzip heißt geringstmögliche Rechte: Ein Programm darf nur das, was es wirklich braucht. Hätte das Archiv-Skript einen Fehler oder bekäme es manipulierte Daten, könnte es trotzdem nichts außerhalb seines Ordners anrichten.
!ende

# Phase 1: Daten laden und eigenes Archiv

## Der Trainingsdownload, Schritt für Schritt

Das Skript `scripts/download.py` läuft als eigener systemd-Dienst `smard-forecast-download`, damit es unabhängig von einer offenen Sitzung weiterläuft.

1. Ortsliste lesen; je Ort die Variablen bestimmen (Solar 6, Wind 6, beides 10).
2. Den Zeitraum 22.02.2024 bis 01.11.2026 in Kalenderjahre teilen: drei Stücke je Ort, 120 insgesamt.
3. Stücke überspringen, deren Datei schon existiert (`data/wetter/<ort>/<von>_<bis>.parquet`). Dadurch kann der Download jederzeit abbrechen und weitermachen.
4. Für jedes offene Stück das Gewicht berechnen (Formel oben, 78 bis 156).
5. Prüfen, ob das Gewicht in alle drei Zeitfenster passt (nächster Abschnitt); sonst warten.
6. Abruf; bei leerer Antwort, Zeitüberschreitung oder Statuscode 429 oder 5xx bis zu fünfmal wiederholen, mit wachsender Pause.
7. Abruf mit Zeitpunkt und Gewicht in `data/wetter/budget.json` buchen.
8. Antwort in die lange Form bringen und als Parquet speichern; erst in eine `.tmp`-Datei, dann umbenennen, damit eine halb geschriebene Datei nie als fertig gilt.
9. Eine Zeile ins Protokoll `data/logs/download.log`.

## Gleitende Zeitfenster

Wie stellt man sicher, dass in **keiner** Minute mehr als 450 und in **keiner** Stunde mehr als 4.500 Einheiten abgerufen werden? Mit gleitenden Fenstern: Vor jedem Abruf mit Gewicht w zum Zeitpunkt t wird geprüft

$$ \sum_{t_k > t - 60\,\mathrm{s}} w_k + w \leq 450, \qquad \sum_{t_k > t - 3600\,\mathrm{s}} w_k + w \leq 4500, \qquad \sum_{t_k \geq 0{:}00\,\mathrm{UTC}} w_k + w \leq 9000

!begriff Gleitendes Fenster: ein Zeitraum fester Länge, der immer bis zum aktuellen Augenblick reicht, also mitwandert. Im Gegensatz dazu beginnt ein festes Fenster zu festen Zeiten (etwa „jede volle Stunde“).

Die Grenzen liegen absichtlich unter denen von Open-Meteo (600, 5.000, 10.000), als Sicherheitsabstand: Open-Meteo zählt vielleicht etwas anders, und andere Abrufe derselben Maschine zählen mit.

## Das eigene Archiv

Warum ein eigenes Archiv, wenn Open-Meteo eins hat? Drei Gründe: Tag 7 gibt es dort nicht; die Überwachung im Betrieb braucht genau die Vorhersagen, die zum Zeitpunkt einer Prognose vorlagen; und ein fremdes Archiv kann Lücken bekommen oder eingestellt werden.

[abb archiv_ablauf | Was der Archiv-Job jede Stunde tut.]

1. Der Timer startet den Dienst stündlich um :35.
2. Der Dienst liest für vier Modelle die Datei `meta.json` von Open-Meteo und darin den Startzeitpunkt des letzten Laufs. Das kostet kein Kontingent.
3. Hat sich der Lauf von ICON-D2, ICON-EU oder ICON global gegenüber dem letzten gespeicherten Stand geändert? D2-RUC wird nur mitgeschrieben, nicht als Auslöser genutzt; sonst wären es 24 Abrufe am Tag.
4. Wenn ja: ein Abruf mit allen 40 Orten kommagetrennt, 10 Variablen, 8 Tage (Gewicht 40).
5. Speichern als `/var/lib/smard-forecast/archiv/JJJJ/MM/TT/<Zeit>.json.gz`, mit Abrufzeit, Modell und allen Laufzeitpunkten.

!begriff gzip: ein verbreitetes Verfahren, um Dateien verlustfrei zu verkleinern. Es ersetzt Wiederholungen durch Verweise auf frühere Stellen. JSON mit vielen ähnlichen Zahlen schrumpft dabei stark.

Gesichert wird das Archiv jede Nacht um 04:00 UTC: Die Dienste-Sicherung der großen Maschine holt es als Archivdatei ab, prüft sie und hebt mehrere Stände auf.

# Phase 2: das Solar-Modell

Solar kommt zuerst, weil es am besten vorhersagbar ist und sein Fehler am klarsten zu messen. Schlägt Solar die Messlatten nicht, lohnt sich der Rest nicht. Dieses Kapitel beschreibt Versuchsaufbau, Ergebnisse und die daraus gezogenen methodischen Folgerungen; es ist bewusst im Stil eines Ergebnisteils einer wissenschaftlichen Arbeit geschrieben. Wahrscheinlichkeitsprognosen für Wind- und Solarleistung sind ein etabliertes Forschungsfeld; einen Überblick über Verfahren und Bewertung geben [@!hong2016], speziell für Photovoltaik [@!antonanzas2016] und für Wind [@!pinson2013]. Das hier verwendete Vorgehen, Gradient Boosting mit Quantilverlust auf Wettermodellausgaben, gehört zu den Verfahren, die in diesem Feld regelmäßig gut abschneiden [@hong2016]. Alle Zahlen stammen unmittelbar aus den Ergebnisdateien in `data/phase2/` und werden beim Bau dieses Dokuments eingelesen.

## Versuchsaufbau

**Datenbasis.** Eine Beobachtung ist ein Paar aus einer SMARD-Stunde t und einem Vorlauftag N ∈ {1, …, 6}. Nach Nachtmaske und Entfernung vollständig fehlender Wetterzeilen bleiben {{z:sol_zeilen}} Beobachtungen mit {{z:sol_merkmale}} Merkmalen (126 Wetterspalten der 21 Solar-Orte, 6 Mittelwerte über alle Orte, 8 Kalendermerkmale, der Vorlauftag). Die Nachtmaske entfernt alle Stunden, in denen an keinem der Solar-Orte die Sonne über dem Horizont steht; in diesen Stunden liegt nur {{z:sol_nacht_pct:3}} % der gemessenen Solarenergie.

**Zielgröße.** Gelernt wird die Auslastung, also die Erzeugung bezogen auf die installierte Leistung des Monats m(t):

$$ a_t = \frac{E_t}{P_{\mathrm{inst},\,m(t)} \cdot 1\,\mathrm{h}} \in [0, 1]

Die Normierung trennt das Wettersignal vom Zubau: Eine Stunde im Juni 2024 und eine im Juni 2026 sind bei gleichem Wetter gleich viel wert, obwohl 2026 deutlich mehr Leistung installiert ist.

**Validierungsschema.** Für jeden Testmonat M mit Beginn t_M wird nur mit Beobachtungen trainiert, deren Zielstunde mindestens Δ vor t_M liegt:

$$ \mathcal{D}_M^{\mathrm{train}} = \{ (x_i, a_i) : t_i < t_M - \Delta \}, \qquad \Delta = 7\,\mathrm{d}

!begriff Sicherheitsabstand: eine Lücke zwischen Trainingsende und Testbeginn. Hier 7 Tage, weil eine Vorhersage mit 6 Tagen Vorlauf zu einem Zeitpunkt entsteht, an dem die Messwerte der letzten 6 Tage vor der Zielstunde noch nicht existieren. Ohne den Abstand hätte das Modell beim Prüfen Wissen, das es im Betrieb nie hat. Englisch: gap oder embargo.

Getestet wird rollierend über alle Monate von März 2025 bis Juli 2026, dazu einmalig der Abschlusstest August bis Oktober 2026 (Kapitel 15). Hyperparameter sind die Startwerte aus Kapitel 13 (15 Blätter, 300 Bäume, Lernrate 0,05, mindestens 50 Zeilen je Blatt, je 80 % der Merkmale und Zeilen je Baum).

**Kennzahlen.** Neben MAE und Trefferquote (Kapitel 9 und 10) wird der mittlere Pinball-Verlust über die drei Quantile berichtet, in Prozentpunkten der Leistung [@madsen2005]:

$$ \bar{L} = \frac{1}{3} \sum_{\tau \in \{0{,}1;\ 0{,}5;\ 0{,}9\}} \frac{1}{n} \sum_{i=1}^{n} L_\tau\left(a_i, \hat{q}_\tau(x_i)\right)

Tabelle: Was je Vorlauftag berichtet wird
| Kennzahl | Definition | Ziel |
| MAE | Mittel von abs(a − p50), in % der Leistung und in GW | klein |
| Fehler der Tagesenergie | Betrag der Tagessumme von (a − p50) mal Leistung, in GWh | für Tagesfragen |
| Trefferquote | Anteil Stunden mit p10 ≤ a ≤ p90 | 75 bis 85 % |
| mittlerer Pinball-Verlust | Formel oben | klein |
| Skill | 1 − MAE Modell / MAE der besseren einfachen Messlatte | mindestens 0,2 |

## Diagnose: Unteranpassung oder Verteilungsverschiebung?

Für eine zu geringe Trefferquote gibt es zwei grundsätzlich verschiedene Erklärungen, die verschiedene Gegenmittel verlangen:

1. **Unteranpassung.** Die Quantilmodelle haben die bedingten Quantile nicht gelernt, etwa weil 300 flache Bäume nicht ausreichen. Dann müsste die Trefferquote schon auf den Trainingsdaten selbst deutlich unter 80 % liegen; Gegenmittel wäre ein größeres Modell.
2. **Verteilungsverschiebung.** Die Fehlerverteilung ändert sich zwischen den Monaten, etwa durch Jahreszeit, Wetterregime oder Änderungen im Wettermodell. Dann stimmt die Trefferquote im Training, aber nicht in einem späteren Monat; Gegenmittel ist eine Kalibrierung aus jüngeren Fehlern.

!begriff Verteilungsverschiebung: der Fall, dass die Daten im Betrieb anders verteilt sind als im Training, sodass ein Modell, das im Training richtig lag, später systematisch danebenliegt. Englisch: distribution shift. Zeitreihen aus Wetter und Energie sind dafür besonders anfällig, weil sich Klima, Anlagenpark und Wettermodelle laufend ändern.

Der Test fiel eindeutig aus: Auf einer Stichprobe der Trainingsdaten lag die Trefferquote bei {{z:sol_diag_train:1}} %, im Testmonat März 2026 bei {{z:sol_diag_test:1}} %. Die Quantile sind also gelernt. Die zu schmalen Bänder in anderen Monaten gehen auf Unterschiede zwischen den Monaten zurück.

Zur Gegenprobe wurden größere Modelle auf jedem dritten rollierenden Monat geprüft:

!begriff Hyperparameter-Raster: eine kleine, vorab festgelegte Menge von Einstellungen, die alle unter denselben Bedingungen geprüft werden. Vorab festgelegt, damit nicht so lange gesucht wird, bis ein Zufallstreffer gut aussieht. Englisch: grid search.

## Konforme Quantilregression

Die Diagnose verlangt eine Korrektur der Bandbreite, die aus Fehlern außerhalb der Trainingsdaten gelernt wird. Das Standardverfahren dafür ist die konforme Quantilregression nach [@!romano2019]; eine Einführung geben [@!angelopoulos2023].

!begriff Konforme Vorhersage: eine Familie von Verfahren, die ein beliebiges Vorhersagemodell nachträglich so korrigiert, dass seine Intervalle eine vorgegebene Trefferquote einhalten [@vovk2005; @angelopoulos2023]. Grundlage ist allein die Rangfolge von Fehlern auf Daten, die das Modell nicht gesehen hat. Englisch: conformal prediction.

!begriff CQR: konforme Quantilregression (conformalized quantile regression). Die Bandbreite aus p10 und p90 wird an beiden Seiten um denselben Betrag verbreitert oder verengt, sodass auf einer Kalibriermenge genau der gewünschte Anteil der Werte hineinfällt.

Für jede Beobachtung i der Kalibriermenge wird zuerst ein Nichtkonformitätsmaß berechnet, der vorzeichenbehaftete Abstand des Messwerts zum nächstgelegenen Bandrand:

$$ s_i = \max\left(\hat{q}_{0{,}1}(x_i) - a_i,\ a_i - \hat{q}_{0{,}9}(x_i)\right)

!begriff Nichtkonformitätsmaß: eine Zahl, die angibt, wie schlecht ein Messwert zur Vorhersage passt. Hier: negativ, wenn der Wert innerhalb der Bandbreite lag (Betrag = Abstand zum näheren Rand), positiv, wenn er außerhalb lag.

Bei n Kalibrierwerten und dem Ziel 1 − α = 0,8 ist der Zuschlag das empirische Quantil

$$ \hat{Q} = \mathrm{Quantil}_{\,(1-\alpha)(1+1/n)}\left(s_1,\ s_2,\ \ldots,\ s_n\right)

und das korrigierte Intervall lautet

$$ C(x) = \left[\hat{q}_{0{,}1}(x) - \hat{Q},\ \hat{q}_{0{,}9}(x) + \hat{Q}\right] \cap [0, 1]

Der Faktor (1 + 1/n) ist eine Endlichkeitskorrektur. Sind Kalibrier- und Testdaten austauschbar, garantiert die Konstruktion P(a ∈ C(x)) ≥ 1 − α, unabhängig davon, wie gut das zugrunde liegende Modell ist [@romano2019]. Ist das Band zu breit, wird der Zuschlag negativ und verengt es.

!begriff Austauschbarkeit: eine Folge von Zufallsgrößen ist austauschbar, wenn ihre gemeinsame Verteilung sich nicht ändert, wenn man die Reihenfolge vertauscht [@vovk2005]. Unabhängige, gleich verteilte Daten sind austauschbar, Zeitreihen im Allgemeinen nicht. Englisch: exchangeability.

!achtung Die Garantie gilt hier nur näherungsweise
Stündliche Energiedaten sind autokorreliert und saisonal, also nicht austauschbar. Die Überdeckungsgarantie gilt deshalb formal nicht; ob die Korrektur trägt, muss empirisch geprüft werden [@barber2023]. Genau das leisten die rollierende Prüfung und später die Überwachung im Betrieb.
!ende

**Leckfreie Umsetzung.** Die Korrektur für Testmonat M wird ausschließlich aus Vorhersagen der rollierenden Monate vor M gelernt, und zwar je Vorlauftag getrennt, weil die Unsicherheit mit dem Vorlauf wächst. Der erste rollierende Monat dient nur als Kalibriermenge und wird nicht bewertet. Damit ist jede berichtete Trefferquote eine echte Vorhersage: Weder Modell noch Korrektur haben den bewerteten Monat gesehen.

!warum Warum sind die Netzbetreiber an Tag 1 so viel besser?
Das ist im Projekt nicht untersucht; die folgenden Punkte sind Hypothesen, keine Befunde. Hypothese (3) ließe sich prüfen, indem man die Fehler beider Verfahren gegen eine unabhängige Messung vergleicht.

## Fehlerwachstum mit dem Vorlauf

Von Tag 1 bis Tag 6 wächst der MAE für Solar auf das {{z:sol_faktor:1}}-fache, für Wind an Land auf das {{z:won_faktor:1}}-fache und für Wind auf See auf das {{z:wof_faktor:1}}-fache. Der Unterschied ist physikalisch plausibel: Bei Solar bestimmt der Sonnenstand einen großen, exakt vorhersagbaren Teil des Signals, nur die Bewölkung ist unsicher. Bei Wind hängt praktisch alles an der Lage und Stärke von Tiefdruckgebieten, deren Vorhersagbarkeit nach wenigen Tagen chaotisch zerfällt (Kapitel 8) [@lorenz1963]. Hinzu kommt die steile Leistungskurve: Weil die Leistung im Teillastbereich mit der dritten Potenz der Windgeschwindigkeit steigt (Kapitel 7), wird ein Fehler der Windvorhersage in der Leistung verstärkt [@manwell2009].

[abb e_beispielwoche | Eine Woche des Abschlusstests (12. bis 18. Oktober 2026), Wind an Land, mit Vorlauf 1 Tag (oben) und 5 Tagen (unten).]

Die Beispielwoche zeigt beide Seiten. Mit einem Tag Vorlauf folgt der Median dem Messwert eng, auch durch das Starkwindereignis am 13. und 14. Oktober. Mit fünf Tagen Vorlauf hat das Wettermodell dieses Ereignis zu schwach angekündigt; der Messwert verlässt das Band nach oben. Das Band ist dafür sichtbar breiter, und in den übrigen Tagen liegt der Messwert meist darin. Genau so soll sich eine kalibrierte Wahrscheinlichkeitsprognose verhalten: Sie wird nicht genauer, aber sie gibt ehrlich an, wie ungenau sie ist.

## Wind auf See im Abschlusstest

Für Wind auf See fällt der Abschlusstest deutlich schlechter aus als die rollierende Prüfung, an Tag 6 bis fast auf die Klimatologie. ## Was die Modelle gelernt haben

[abb e_wichtigkeit | Gain-Wichtigkeit der zehn wichtigsten Merkmale der Median-Modelle im Betrieb (Anteil am gesamten Gewinn aller Teilungen).]

!begriff Gain-Wichtigkeit: die Summe der Verlustminderungen aller Teilungen eines Baum-Ensembles, die ein bestimmtes Merkmal verwenden, als Anteil an der Summe über alle Merkmale [@hastie2009]. Sie zeigt, worauf sich das Modell stützt, aber nicht, was ursächlich wirkt.

Die Gewichte sind physikalisch stimmig. Das Solar-Modell stützt sich zu {{z:wicht_solar_top_pct:0}} % auf die mittlere Globalstrahlung über alle Orte, danach auf den Sonnenstand. Beide Wind-Modelle stützen sich vor allem auf die mittlere Windgeschwindigkeit in 100 m Höhe ({{z:wicht_wind_onshore_top_pct:0}} % an Land, {{z:wicht_wind_offshore_top_pct:0}} % auf See), also die Größe, die der Nabenhöhe am nächsten kommt. Der Vorlauftag selbst ist bei Wind unter den wichtigsten Merkmalen: Das Modell lernt, dass dieselbe vorhergesagte Windgeschwindigkeit mit wachsendem Vorlauf weniger verlässlich ist und zieht seine Vorhersage dann zum Mittel hin.

!achtung Grenzen der Gain-Wichtigkeit
Stark korrelierte Merkmale teilen sich die Wichtigkeit beliebig: Die Windgeschwindigkeit an 16 Orten und ihr Mittel tragen fast dieselbe Information, und welches Merkmal ein Baum wählt, ist teilweise Zufall. Außerdem bevorzugt das Maß stetige Merkmale mit vielen möglichen Schwellen [@strobl2007]. Für kausale Aussagen braucht man andere Verfahren, etwa Permutationstests auf zurückgehaltenen Daten.
!ende

# Phase 4: Betriebsmodelle und das Tool in smard-mcp

Phase 4 überführt die Modelle in den Betrieb: Training auf allen Daten, Export, eine unabhängige Auswertung in TypeScript in smard-mcp, das Tool selbst und die Prüfung, dass beide Implementierungen dasselbe rechnen. ## Gütestufen

Jedes Intervall der Ausgabe trägt eine Gütestufe. Für den Vorlauftag N ist sie aus dem schlechteren der beiden gemessenen Skill-Werte abgeleitet:

$$ S_N = \min\left(S_N^{\mathrm{rollierend}},\ S_N^{\mathrm{Abschluss}}\right), \qquad \mathrm{Stufe}(N) = \mathrm{high}\ (S_N \geq 0{,}4),\ \ \mathrm{medium}\ (S_N \geq 0{,}2),\ \ \mathrm{low}\ (\mathrm{sonst})

Liegt eine Stunde zwischen zwei Vorlauftagen (Interpolation, Kapitel 16), gilt die schlechtere der beiden Stufen, für einen Tag die schlechteste seiner Stunden. Die Stufen stehen in der Modelldatei und werden bei jedem neuen Training aus den Kennzahlen neu berechnet.

## Ablauf einer Anfrage

[abb l_mcp | Ablauf einer Anfrage, vom Menschen über den KI-Assistenten und smard-mcp zu den Datenquellen und zurück (Schema).]

1. Wetter holen: ein Abruf der Forecast API für alle 40 Orte (Gewicht 40), zwischengespeichert, bis `meta.json` eines der drei ICON-Modelle einen neueren Lauf meldet.
2. Für jede Stunde den Lauf bestimmen, der sie abdeckt: ICON-D2, solange dessen Daten reichen, dann ICON-EU, dann ICON global. Der Vorlauf L ist die Stunde minus den Start dieses Laufs.
3. Merkmale bauen, genau wie im Training (gleiche Ausrichtung, gleiche Spaltenreihenfolge aus der Modelldatei).
4. Für die beiden benachbarten Vorlauftage je drei Quantile auswerten, sortieren [@chernozhukov2010], auf [0, 1] begrenzen, mit der CQR verbreitern und linear mischen (Kapitel 16). Solar nachts auf 0.
5. Mit der installierten Leistung des Monats in GW umrechnen; je Tag zu GWh summieren.
6. Die Prognose der Netzbetreiber daneben stellen, soweit veröffentlicht.
7. Ausgabe mit Hinweis, Gütestufen, Modellversion und Wetterläufen.

Der Horizont endet, wo der längste trainierte Vorlauf erreicht ist: (L − 3 h) / 24 h ≤ 6, also L ≤ 147 h nach dem Start des globalen Laufs. Spätere Stunden wären Extrapolation über den Trainingsbereich hinaus.

## Prüfung der Interpolation

Kapitel 16 begründet, warum der Vorlauf zwischen den Vorlauftagen interpoliert statt abgerundet wird. Geprüft wird das an echten Einzelläufen aus der Single Runs API: Für Läufe von Mai bis Oktober 2026 wird jede Stunde mit ihrem tatsächlichen Vorlauf einmal interpoliert und einmal abgerundet vorhergesagt, mit Modellen, die nur Daten bis Ende April kennen. Verglichen werden Trefferquote und MAE je 6-Stunden-Band des Vorlaufs.

!achtung Ergebnis steht noch aus
Die Single Runs API setzt `icon_seamless` für jeden Ort bei der Anfrage neu zusammen und braucht dafür rund eine Minute je Ort. Geladen werden deshalb nur 13 Läufe im Abstand von 15 Tagen; zum Stand dieses Dokuments lagen {{z:interp_laeufe}} vor. Ein Probelauf auf dem ersten Lauf bestätigte nur, dass die Auswertung technisch durchläuft; aus einem einzigen Lauf lässt sich nichts schließen. Das Ergebnis wird in diesem Abschnitt nachgetragen.
!ende

## Numerische Äquivalenz von Python und TypeScript

smard-mcp soll keine neue Abhängigkeit bekommen und rechnet die Modelle deshalb selbst aus. Damit gibt es zwei unabhängige Implementierungen derselben Rechnung, und es muss nachgewiesen werden, dass sie übereinstimmen.

**Format.** Der Export wandelt jedes LightGBM-Modell in parallele Listen je Baum um:

```
// models/wind_onshore_p50.json (ein Baum, gekürzt)
{ "merkmale": ["husum__wind_speed_10m", ..., "vorlauf_tag"],
  "baeume": [ { "f": [97, 3, ...],          // Merkmal je Knoten
                "t": [21.35, 0.4, ...],     // Schwelle je Knoten (float64, exakt)
                "m": [0, 2, ...],           // fehlender Wert: 0 keiner, 1 Null, 2 NaN
                "d": [1, 0, ...],           // 1 = fehlender Wert geht nach links
                "l": [1, -1, ...], "r": [2, -2, ...],  // Kinder; negativ = Blatt Nr. -(i+1)
                "v": [-0.0123, 0.004, ...] } ] }       // Blattwerte
```

**Entscheidungsregel.** An jedem Knoten folgt die Auswertung der Regel von LightGBM: Ein fehlender Wert (NaN) zählt als 0, außer der Knoten behandelt NaN gesondert; ein fehlender Wert im Sinn des Knotens geht in die Standardrichtung; sonst gilt x ≤ Schwelle → links [@lightgbmdoc]. Die Vorhersage ist die Summe der erreichten Blattwerte über alle Bäume:

$$ \hat{q}_\tau(x) = \sum_{k=1}^{K} v_k\left(l_k(x)\right)

wobei l_k(x) das Blatt ist, in dem x im Baum k landet, und v_k dessen Wert. Der Startwert und die Lernrate sind in den Blattwerten bereits enthalten.

```
export function predictTree(tree: CompactTree, x: ArrayLike<number>): number {
  let node = 0;
  for (;;) {
    let value = x[tree.f[node]];
    const missing = tree.m[node];
    if (Number.isNaN(value) && missing !== 2) value = 0;
    const isMissing = (missing === 1 && Math.abs(value) <= 1e-35) || (missing === 2 && Number.isNaN(value));
    const left = isMissing ? tree.d[node] === 1 : value <= tree.t[node];
    const next = left ? tree.l[node] : tree.r[node];
    if (next < 0) return tree.v[-next - 1];
    node = next;
  }
}
```

**Vergleichstest.** Das Skript `phase4_vergleich.py` holt die aktuelle Vorhersage aller 40 Orte, genau den Abruf, den das Tool macht, und rechnet sie mit Python durch: Merkmale, beide Vorlauftage, CQR, Mischung, Nachtmaske. Eingabe und Ergebnis werden gespeichert; der Test in smard-mcp rechnet dieselbe Eingabe in TypeScript nach. Kriterium: Für alle 192 Stunden und alle drei Quellen weichen p10, p50 und p90 um weniger als 10⁻⁶ ab.

Gleitkommazahlen (Begriff in Kapitel 19) folgen dem Standard IEEE 754: Vorzeichen, Mantisse und Exponent zur Basis 2 [@ieee754; @goldberg1991]. Eine float32-Zahl hat 24 Bit Mantisse (relative Genauigkeit etwa 6·10⁻⁸), eine float64-Zahl 53 Bit (etwa 1·10⁻¹⁶). JavaScript rechnet immer in float64; pandas behält float32, wenn die Daten so gespeichert sind.

Der erste Vergleich zeigte für Solar Übereinstimmung, für Wind aber Abweichungen bis 0,7 % der Leistung. Ursache war die Mittelung über alle Orte: pandas summiert float32-Spalten in float32, TypeScript rechnete in float64. Beim Luftdruck genügen wenige Bit, um eine Schwelle zu kippen:

!rechnen Wie groß ein Bit beim Luftdruck ist
Ein Luftdruck von 1013 hPa liegt zwischen 2⁹ = 512 und 2¹⁰ = 1024. In float32 ist der Abstand benachbarter Zahlen dort 2⁹ · 2⁻²³ = 2⁻¹⁴ ≈ 6,1·10⁻⁵ hPa. Liegt eine gelernte Schwelle eines Baums genau zwischen dem float32- und dem float64-Ergebnis des Mittels, landet die Zeile in verschiedenen Blättern, und mit ihr ändert sich die Vorhersage um den Unterschied zweier Blattwerte.
!ende

TypeScript bildet die float32-Rechnung seitdem mit `Math.fround` nach, einschließlich der Summation in float32. Danach erfüllen alle drei Quellen das Kriterium. Diese Art Fehler ist typisch für Baummodelle: Ein stetiges Modell hätte die Abweichung von 10⁻⁵ hPa praktisch nicht weitergegeben, ein Baum gibt sie als Sprung weiter.

## Tagesenergie als Summe von Quantilen

Die Tageswerte p10 und p90 sind Summen der stündlichen Quantile. Das ist eine Näherung. Quantile sind im Allgemeinen nicht additiv; exakt gilt die Summenregel nur bei Komonotonie [@dhaene2002]:

$$ q_\tau\left(\sum_h X_h\right) = \sum_h q_\tau\left(X_h\right) \quad \mathrm{falls}\ X_1, \ldots, X_{24}\ \mathrm{komonoton}

!begriff Komonotonie: mehrere Zufallsgrößen heißen komonoton, wenn sie alle steigende Funktionen ein und derselben Zufallsgröße sind; sie bewegen sich dann immer gemeinsam in dieselbe Richtung [@dhaene2002]. Für Prognosefehler hieße das: Liegt die Vorhersage um 10 Uhr zu hoch, liegt sie auch um 11 und um 12 Uhr im selben Maß zu hoch.

Die Fehler aufeinanderfolgender Stunden sind stark positiv abhängig, weil sie meist auf dieselbe falsch vorhergesagte Wetterlage zurückgehen (Kapitel 9, Autokorrelation), aber nicht vollständig. Bei schwächerer Abhängigkeit gleichen sich Fehler teilweise aus, und das wahre Band der Tagessumme ist in aller Regel schmaler als die Summe der stündlichen Bänder. Die ausgegebenen Tagesbänder sind also eher zu breit als zu schmal; das Tool sagt das in `notes`. Ob ihre Trefferquote tatsächlich über 80 % liegt, lässt sich im Betrieb messen.

## Die Modellbeschreibung

Das zweite Tool, `describe_forecast_model`, gibt eine knappe technische Beschreibung des Modells zurück: Zielgröße, Wetterdaten, Verfahren und Hyperparameter, Merkmale, Behandlung des Vorlaufs, Kalibrierung, Prüfschema, Annahmen zur installierten Leistung, die gemessenen Kennzahlen je Quelle und Vorlauftag (MAE, Trefferquote, Skill, Gütestufe, Breitenzuschlag) und die bekannten Grenzen. Kein Wert darin ist von Hand geschrieben: Prüfzeiträume, Schwellen der Gütestufen, die Liste der als „low“ eingestuften Tage und der Vergleich mit den Netzbetreibern werden aus der Modelldatei gelesen, die der Export aus den Ergebnisdateien erzeugt. Nach jedem Neu-Training stimmt die Beschreibung deshalb automatisch.

## Wetterabruf und Zwischenspeicher

Der HTTP-Server von smard-mcp erzeugt für jede Anfrage eine neue Server-Instanz. Ein Wetter-Client je Instanz hätte deshalb bei jeder Anfrage Open-Meteo gefragt, mit Gewicht 40 je Abruf, und nach rund 250 Anfragen am Tag das Tageslimit erreicht. Der Client ist deshalb prozessweit geteilt; ein Test prüft, dass zwei Server-Instanzen mit zwei Anfragen genau einen Abruf auslösen. So wird Open-Meteo etwa einmal je neuem Modelllauf gefragt, rund achtmal am Tag. Die Rechnung selbst (Merkmale und neun Modelle für alle Stunden) dauert etwa 150 ms und wird je Wetterlauf ebenfalls nur einmal ausgeführt.

# Phase 5 und 6: Überwachung, Neu-Training, Ausrollen

## Tägliche Überwachung

Ein täglicher Job nimmt die archivierten Vorhersagen, rechnet mit dem aktuellen Modell die Prognose, die das Tool damals ausgegeben hätte, und vergleicht sie mit den inzwischen veröffentlichten SMARD-Werten. Geplant ist, MAE und Trefferquote der letzten 30 Tage je Vorlauftag in jeder Antwort des Tools auszugeben; die erste Fassung enthält nur die Werte aus der Prüfung. So sähe jeder Nutzer, wie verlässlich die Zahlen gerade sind, nicht nur wie gut sie im Test waren. Das Lernbeispiel zur Kalibrierung (Kapitel 10) zeigt, warum das nötig ist: Fehler können sich von Jahr zu Jahr verändern.

## Monatliches Neu-Training

[abb workflow | Automatisch bis zum Pull Request, gemergt wird nur von Hand.]

!begriff GitHub Actions: ein Dienst von GitHub, der Programme automatisch ausführt, etwa zu festen Zeiten oder nach jedem Push. Eine Beschreibung in einer Datei (Workflow) legt fest, was wann läuft.

!begriff Pull Request: ein Vorschlag, Änderungen in den Hauptzweig eines Repositorys zu übernehmen. Man kann ihn ansehen, kommentieren und dann übernehmen (mergen) oder ablehnen.

## Ausrollen und Prüfpunkt C

1. Tool auf einem Nebenzweig in smard-mcp, Tests grün, TypeScript gegen Python geprüft.
2. Ausrollen nur mit `npm run deploy` (verlangt einen sauberen, gepushten Stand, führt die Tests aus, sichert die alte Version, prüft nach dem Start, ob der Dienst antwortet, und rollt sonst automatisch zurück).
3. Zwei bis vier Wochen den Fehler im Betrieb beobachten.
4. **Prüfpunkt C:** Ist der Fehler im Betrieb ähnlich wie im Abschlusstest? Dann Veröffentlichung als neue Version bei npm, sonst nachbessern.

# Betrieb, Kosten und Risiken

Tabelle: Laufende Kosten
| Was | Wie oft | Kosten |
| Archiv-Job | stündlich prüfen, etwa 8 Abrufe am Tag | 320 Einheiten am Tag, 300 MB im Jahr |
| Wetter für das Tool | bei neuem Lauf, etwa 8 Abrufe am Tag | 320 Einheiten am Tag |
| Anfrage an das Tool | je Anfrage | Millisekunden Rechenzeit |
| Überwachung | täglich | Sekunden |
| Neu-Training | monatlich | Minuten Rechenzeit, unter 1 GB Speicher |
| Erstdownload | einmalig | etwa 10.460 Einheiten, zwei Tage |

Geldkosten fallen keine an.

Tabelle: Risiken
| Risiko | Folge | Gegenmaßnahme |
| Lücken im ICON-Archiv | weniger Trainingsdaten | geprüft: nur ein Ausfall; eigenes Archiv |
| Abregelung bei negativen Preisen | Erzeugung unter dem Wetterwert | Wochentag und Feiertag als Merkmal, Hinweis in notes |
| Zubau | systematischer Versatz | Monatswerte statt SMARD-Jahreswerte |
| seltene Wetterlagen (Dunkelflaute, Sturm) | grobe Ausreißer | Quantile; Winter getrennt bewertet |
| Open-Meteo ändert Bedingungen oder fällt aus | keine Prognose | Zwischenspeicher mit Warnung; langfristig DWD Open Data als zweite Quelle |
| Wechsel innerhalb von icon_seamless | Eingaben verändern sich | Laufzeitpunkte im Archiv, Überwachung zeigt Brüche |
| Lizenz Energy-Charts | Nenner fehlt; die Monatswerte stehen in der Modelldatei, die mit dem npm-Paket verteilt würde | vor dem Mergen klären; Rückfall Marktstammdatenregister |
| Abweichung zwischen Python und TypeScript | Tool rechnet anders als geprüft | Vergleichstest auf echter Eingabe, Toleranz 10⁻⁶ |
| Tageslimit von Open-Meteo | keine Prognose | ein prozessweiter Zwischenspeicher, Abruf nur bei neuem Lauf |
| Unsicherheit hängt von der Jahreszeit ab | Bänder im Winter zu schmal, im Sommer zu breit | Überwachung; später Kalibrierung nach Jahreszeit |
